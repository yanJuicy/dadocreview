### #ERR-004: 포트 충돌로 인한 서버 접속 불가
- **현상:** 브라우저 `ERR_CONNECTION_REFUSED` + 서버 재시작 시 `Address already in use`
- **원인:** 이전 uvicorn 프로세스가 포트 8000을 점유한 채 종료되지 않음
- **해결:** `kill -9 $(lsof -t -i:8000)` → 가상환경 활성화 → 서버 재시작

## 3️⃣ 핵심 학습 개념 — 예외 처리 심층 토론

오늘 세션에서 사용자와 AI 간 예외 처리 철학에 대한 깊이 있는 Q&A가 이루어졌다. 실무에서 주니어와 시니어를 가르는 중요한 사고방식이므로 기록한다.

### 💡 Q1. "왜 예외 처리(try-except)를 해 놓고 raise로 또 예외를 발생시키는 거야?"

**A:** `try-except`와 `raise`는 역할이 다르다.
- **`try-except`**: 프로그램이 **비명횡사(Crash)하는 것을 막는 방어막**이다. 예측할 수 없는 사고(네트워크 장애, 외부 서버 다운)로부터 프로그램을 보호한다.
- **`raise HTTPException`**: 프로그램을 보호한 후, **사용자(브라우저)에게 "이런 상황이 발생했다"고 공식적으로 통지**하는 행위이다. FastAPI가 이 신호를 받아 적절한 HTTP 상태 코드(404, 503 등)를 사용자에게 보내준다.

### 💡 Q2. "return을 해야 사용자에게 돌려주는 거 아니야?"

**A:** 맞다. 정상 상황에서는 `return`이 정답이다. 하지만 FastAPI에는 **'비상벨 시스템'**이 있다.
- `return`은 점원이 음식을 정상 전달하는 것이고, `raise HTTPException`은 비상벨을 눌러서 FastAPI가 대신 에러 응답을 만들어 보내게 맡기는 것이다.
- `raise`를 쓰면 에러 상황을 먼저 쳐내버리고(**Early Exit / Guard Clause**), 이후 코드는 "무조건 성공한 상황"에만 집중해서 깔끔하게 작성할 수 있다.

### 💡 Q3. "왜 naru_api는 try-except인데 main.py는 if + raise야?"

**A:** **"예측 가능성"**의 차이다.
- **`try-except` (예측 불가능한 사고)**: 정보나루 서버가 죽거나 네트워크가 끊기는 건 우리가 예측할 수 없는 '사고'이다. 일단 실행(`try`)해보고 사고가 나면 수습(`except`)한다.
- **`if ... raise` (예측 가능한 규칙 위반)**: 사용자가 없는 책 ID를 입력하는 건 충분히 '예상되는 상황'이다. DB 조회 결과가 `None`인 것은 Python 입장에서 에러가 아니지만, 비즈니스 관점에서 404 에러로 처리해야 한다.

**레이어 분리 원칙:**
- 서비스(`naru_api.py`, `scraper.py`): HTTP를 모르는 레이어. 데이터를 가져오거나, 못 가져오면 빈 통(`[]`)을 조용히 반환한다.
- 라우터(`main.py`): HTTP를 아는 레이어. 데이터의 유무를 판단하고, 사용자에게 어떤 표정(200, 404 등)을 지을지 결정한다.

### 💡 Q4. "raise를 쓰면 에러 해결을 안 해도 되는 거야?"

**A:** `raise`는 "에러를 무시하는 것"이 아니라, **"에러를 가장 안전하고 명확하게 마무리짓는 것"**이다.
- 해결 가능한 에러: `return []`로 대안을 제시 (Graceful Degradation)
- 해결 불가능한 에러: `raise`로 프로그램을 안전하게 멈추고 **정확한 이유를 알려줌** (존재하지 않는 책을 새로 만들어낼 순 없음)
- 억지로 `return`을 해서 대충 넘기면, 나중에 데이터가 꼬여서 DB가 망가지는 등 훨씬 큰 2차 사고가 날 수 있다.

## 📝 학습 키워드

오늘 작업에서 체득한 핵심 개념들:

- **Graceful Degradation** — 한 부분(외부 API)이 실패해도 전체 서비스가 멈추지 않게 하는 전략
- **Guard Clause (Early Exit)** — 에러 조건을 함수 초반에 `raise/return`으로 쳐내어 코드 가독성을 높이는 패턴
- **Exception Handling vs Error Signaling** — `try-except`(사고 수습)와 `if...raise`(규칙 위반 신고)의 용도 구분
- **레이어 분리 원칙** — 서비스 레이어는 HTTP를 모르게, 라우터 레이어에서만 HTTP 상태 코드를 결정하게
- **포트 충돌 해결** — `lsof`, `fuser`, `kill` 명령어를 활용한 프로세스 관리
