## 2026-04-26 — 예외 처리 심층 토론

### 💡 Q1. "왜 예외 처리(try-except)를 해 놓고 raise로 또 예외를 발생시키는 거야?"

**A:** `try-except`와 `raise`는 역할이 다릅니다.
- **`try-except`**: 프로그램이 **비명횡사(Crash)하는 것을 막는 방어막**입니다. 예측할 수 없는 사고(네트워크 장애, 외부 서버 다운)로부터 프로그램을 보호합니다.
- **`raise HTTPException`**: 프로그램을 보호한 후, **사용자(브라우저)에게 "이런 상황이 발생했다"고 공식적으로 통지**하는 행위입니다. FastAPI가 이 신호를 받아 적절한 HTTP 상태 코드(404, 503 등)를 사용자에게 보내줍니다.

### 💡 Q2. "return을 해야 사용자에게 돌려주는 거 아니야?"

**A:** 맞습니다. 정상 상황에서는 `return`이 정답입니다. 하지만 FastAPI에는 **'비상벨 시스템'**이 있습니다.
- `return`은 점원이 음식을 정상 전달하는 것이고, `raise HTTPException`은 비상벨을 눌러서 FastAPI가 대신 에러 응답을 만들어 보내게 맡기는 것입니다.
- `raise`를 쓰면 에러 상황을 먼저 쳐내버리고(**Early Exit / Guard Clause**), 이후 코드는 "무조건 성공한 상황"에만 집중해서 깔끔하게 작성할 수 있습니다.

### 💡 Q3. "왜 naru_api는 try-except인데 main.py는 if + raise야?"

**A:** **"예측 가능성"**의 차이입니다.
- **`try-except` (예측 불가능한 사고)**: 정보나루 서버가 죽거나 네트워크가 끊기는 건 우리가 예측할 수 없는 '사고'입니다. 일단 실행(`try`)해보고 사고가 나면 수습(`except`)합니다.
- **`if ... raise` (예측 가능한 규칙 위반)**: 사용자가 없는 책 ID를 입력하는 건 충분히 '예상되는 상황'입니다. DB 조회 결과가 `None`인 것은 Python 입장에서 에러가 아니지만, 비즈니스 관점에서 404 에러로 처리해야 합니다.

**레이어 분리 원칙:**
- 서비스(`naru_api.py`, `scraper.py`): HTTP를 모르는 레이어. 데이터를 가져오거나, 못 가져오면 빈 통(`[]`)을 조용히 반환합니다.
- 라우터(`main.py`): HTTP를 아는 레이어. 데이터의 유무를 판단하고, 사용자에게 어떤 표정(200, 404 등)을 지을지 결정합니다.

### 💡 Q4. "raise를 쓰면 에러 해결을 안 해도 되는 거야?"

**A:** `raise`는 "에러를 무시하는 것"이 아니라, **"에러를 가장 안전하고 명확하게 마무리짓는 것"**입니다.
- 해결 가능한 에러: `return []`로 대안을 제시 (Graceful Degradation)
- 해결 불가능한 에러: `raise`로 프로그램을 안전하게 멈추고 **정확한 이유를 알려줌** (존재하지 않는 책을 새로 만들어낼 순 없음)
- 억지로 `return`을 해서 대충 넘기면, 나중에 데이터가 꼬여서 DB가 망가지는 등 훨씬 큰 2차 사고가 날 수 있습니다.

## 2026-04-27 — 프론트엔드 비동기 통신(fetch) 안정화

### 💡 Q1. "네트워크 에러인지 아닌지(예: 404 에러) 어떻게 파악해?"

**A:** JavaScript의 `fetch` API는 에러를 두 가지로 나누어 처리합니다. 이 구분을 명확히 하는 것이 방어적 코딩의 핵심입니다.

1. **`catch` 블록 (네트워크 장애):** 
   - 서버에 **물리적으로 연결조차 되지 않았을 때** 발생합니다 (인터넷 끊김, 오타 난 URL, 서버 다운).
   - `fetch`가 반환하는 Promise가 거부(reject)되는 유일한 상황입니다.

2. **`!response.ok` (HTTP 에러):**
   - 서버와 **연결은 되었으나**, 서버가 404(Not Found)나 500(Internal Server Error) 같은 에러 코드를 보낸 상황입니다.
   - `fetch` 입장에서는 서버와 대화를 나눴으므로 '성공'으로 간주하여 `catch`로 보내지 않습니다. 따라서 우리가 직접 응답 코드를 확인해야 합니다.

**요약:**
- `catch`는 **"전화기 자체가 고장 난 상황"**
- `!response.ok`는 **"전화는 통했지만 상대방이 화가 나서 전화를 끊은 상황"**으로 비유할 수 있습니다.
